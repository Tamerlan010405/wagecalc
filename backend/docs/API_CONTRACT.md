# Контракт API WageCalc

Базовый путь: `/api/v1`

Все запросы и ответы используют JSON, если явно не указано другое. Время
передается строкой в формате RFC3339. Денежные значения передаются строками с
двумя знаками после точки, например `"64902.00"`.

Периоды передаются только числами:

- `period.year`: год отчетного периода.
- `period.quarter`: номер квартала от `1` до `4`.
- `month_index`: номер месяца внутри квартала от `1` до `3`.

Преобразование `quarter` и `month_index` в человекочитаемые названия месяцев
выполняет frontend.

## Идентификатор, Организация И Название Отчета

Frontend не передает `id` расчета при создании. Уникальный `id` генерирует
backend на стороне application/service-слоя в момент создания расчета. Этот
`id` возвращается в ответе `POST /api/v1/calculations` и далее используется для
точного открытия, удаления и связывания данных расчета.

Входные данные расчета содержат два человекочитаемых поля:

- `org_name`: название организации, для которой создается расчет.
- `title`: название отчета/расчета, которое пользователь видит в истории.

В базе данных связи между таблицами должны строиться через сгенерированный
backend `id` расчета. Название организации и название отчета не являются
техническими ключами связи: они нужны для отображения, истории, будущего поиска
и фильтрации. В дальнейшем список расчетов можно будет фильтровать по
`org_name` и/или `title`; при совпадении названий backend должен возвращать
список подходящих расчетов, а frontend для точного действия должен использовать
конкретный `id` из ответа.

## Формат Ошибки

Все ошибки API возвращаются в одном формате:

```json
{
  "error": {
    "code": "INVALID_REQUEST",
    "message": "Некорректное тело запроса",
    "field": "employees[0].months[1].total_140"
  }
}
```

Поле `field` отсутствует, если ошибка не относится к конкретному полю запроса.

Основные коды ошибок:

- `INVALID_REQUEST`: некорректный JSON или ошибка HTTP-запроса.
- `VALIDATION_ERROR`: JSON корректный, но входные данные не прошли проверку.
- `NOT_FOUND`: расчет не найден.
- `METHOD_NOT_ALLOWED`: HTTP-метод не поддерживается.
- `INTERNAL_ERROR`: внутренняя ошибка сервера.
- `INVALID_PASSWORD_RESET_CODE`: код восстановления пароля неверный, просрочен, уже использован или превышено число попыток.

## Авторизация

API использует cookie-based авторизацию.

После успешной регистрации или входа backend устанавливает HttpOnly cookie:

- `wagecalc_session`: токен пользовательской сессии.

Frontend не должен читать, сохранять или передавать этот токен вручную. Для запросов к защищенным endpoint'ам frontend должен отправлять cookie вместе с запросом.

Пример для frontend:

```js
fetch("/api/v1/calculations", {
  credentials: "include"
})
```

Если frontend обращается к backend по полному URL:

```js
fetch("http://localhost:8080/api/v1/calculations", {
  credentials: "include"
})
```

Защищенные endpoints:

- `POST /api/v1/calculations`
- `GET /api/v1/calculations`
- `GET /api/v1/calculations/{id}`
- `DELETE /api/v1/calculations/{id}`

Auth endpoints:

- `POST /api/v1/auth/register`
- `POST /api/v1/auth/login`
- `POST /api/v1/auth/logout`
- `GET /api/v1/auth/me`
- `POST /api/v1/auth/password-reset/request`
- `POST /api/v1/auth/password-reset/confirm`

Если пользователь не авторизован, cookie отсутствует или сессия истекла, backend возвращает `401 Unauthorized`.

Расчеты изолированы по текущему пользователю. Пользователь видит, получает и удаляет только расчеты организаций, к которым он привязан. Если расчет существует, но принадлежит другому пользователю, backend возвращает `404 Not Found`.

## Зарегистрировать Пользователя

`POST /api/v1/auth/register`

Создает пользователя с email и паролем, создает сессию и устанавливает cookie `wagecalc_session`.

Тело запроса:

```json
{
  "email": "user@example.com",
  "password": "password123",
  "display_name": "User Name"
}
```

Поля:

- `email`: обязательный email пользователя.
- `password`: обязательный пароль, минимум 8 символов и максимум 72 байта
- `display_name`: необязательное отображаемое имя пользователя.

Ответ `201 Created`:

```json
{
  "user": {
    "id": "user-id",
    "email": "user@example.com",
    "display_name": "User Name"
  }
}
```

Возможные ошибки:

- `422 Validation Error`: некорректный email или пароль короче 8 символов.
- `409 Conflict`: пользователь с таким email уже существует.

## Войти

`POST /api/v1/auth/login`

Проверяет email и пароль, создает новую сессию и устанавливает cookie `wagecalc_session`.

Тело запроса:

```json
{
  "email": "user@example.com",
  "password": "password123"
}
```

Ответ `200 OK`:

```json
{
  "user": {
    "id": "user-id",
    "email": "user@example.com",
    "display_name": "User Name"
  }
}
```

Возможные ошибки:

- `401 Unauthorized`: cookie отсутствует, сессия не найдена или сессия истекла.
- `UNAUTHORIZED`: пользователь не авторизован или сессия недействительна.
- `AUTH_IDENTITY_EXISTS`: пользователь с таким способом входа уже существует.
## Запросить Восстановление Пароля

`POST /api/v1/auth/password-reset/request`

Создаёт шестизначный код восстановления пароля и отправляет его на указанный email.

Авторизация и cookie `wagecalc_session` для этого endpoint не требуются.

Тело запроса:

```json
{
  "email": "user@example.com"
}
```

Поля:

- `email`: обязательный email пользователя.

Успешный ответ: `204 No Content`.

Тело ответа отсутствует.

Backend возвращает одинаковый успешный ответ независимо от того, существует ли пользователь с указанным email. Это не позволяет определить зарегистрированные в системе адреса.

Для существующего пользователя:

- создаётся шестизначный код;
- в базе сохраняется только HMAC-хеш кода;
- код действует 15 минут;
- новый код можно запросить не раньше чем через 5 минут;
- при создании нового кода предыдущий неиспользованный код становится недействительным.

Возможные ошибки:

- `400 Bad Request`: некорректный JSON или неизвестные поля.
- `422 Validation Error`: email отсутствует или имеет некорректный формат.
- `500 Internal Server Error`: внутренняя ошибка или письмо не удалось отправить.

## Подтвердить Восстановление Пароля

`POST /api/v1/auth/password-reset/confirm`

Проверяет шестизначный код и устанавливает пользователю новый пароль.

Авторизация и cookie `wagecalc_session` для этого endpoint не требуются.

Тело запроса:

```json
{
  "email": "user@example.com",
  "code": "042731",
  "new_password": "new-password123"
}
```

Поля:

- `email`: обязательный email пользователя.
- `code`: обязательный шестизначный цифровой код из письма.
- `new_password`: обязательный новый пароль, минимум 8 символов.

Успешный ответ: `204 No Content`.

Тело ответа отсутствует.

После успешной смены пароля:

- код помечается использованным и больше не принимается;
- пароль сохраняется в виде bcrypt-хеша;
- все существующие сессии пользователя удаляются;
- пользователь должен заново выполнить `POST /api/v1/auth/login`.

Для одного кода разрешено не более 5 неправильных попыток ввода.

Неверный, просроченный, использованный или заблокированный код возвращает `422 Unprocessable Entity`:

```json
{
  "error": {
    "code": "INVALID_PASSWORD_RESET_CODE",
    "message": "invalid or expired password reset code",
    "field": "code"
  }
}
```

Другие возможные ошибки:

- `400 Bad Request`: некорректный JSON или неизвестные поля.
- `422 Validation Error`: некорректный email, код имеет неверный формат или новый пароль короче 8 символов.
- `500 Internal Server Error`: внутренняя ошибка сервера.
## Создать Расчет

`POST /api/v1/calculations`
Требует авторизации через cookie `wagecalc_session`.

Создает расчет для организации текущего пользователя. Если организация с таким `org_name` уже существует у текущего пользователя, расчет будет привязан к ней. Если не существует, backend создаст новую организацию и привяжет ее к текущему пользователю.

Тело запроса:

```json
{
  "org_name": "ООО Ромашка",
  "title": "Аккредитация за III квартал 2025",
  "period": {
    "year": 2025,
    "quarter": 3
  },
  "threshold": {
    "value_rf": "61328.67",
    "value_region": "70000.00",
    "region_code": "77"
  },
  "employees": [
    {
      "employee_index": 1,
      "months": [
        {
          "month_index": 1,
          "total_140": "100000.00",
          "gph_160": "0"
        },
        {
          "month_index": 2,
          "total_140": "100000.00",
          "gph_160": "0"
        },
        {
          "month_index": 3,
          "total_140": "100000.00",
          "gph_160": "0"
        }
      ]
    },
    {
      "employee_index": 2,
      "months": [
        {
          "month_index": 1,
          "total_140": "90000.00",
          "gph_160": "10000.00"
        },
        {
          "month_index": 2,
          "total_140": "0",
          "gph_160": "0"
        },
        {
          "month_index": 3,
          "total_140": "110000.00",
          "gph_160": "10000.00"
        }
      ]
    }
  ]
}
```

Правила:

- `org_name` обязателен и содержит человекочитаемое название организации.
- `title` обязателен и содержит человекочитаемое название отчета.
- `period.quarter` должен быть числом от `1` до `4`.
- У каждого сотрудника должно быть ровно 3 месяца.
- `month_index` должен быть числом от `1` до `3`.
- Пустое значение выплаты трактуется как `0`.
- Пустое значение планки трактуется как отсутствующая планка.
- API не принимает ФИО, СНИЛС и другие персональные данные сотрудников.

### Лесенка Расчета В Детальном Ответе

Детальный ответ содержит все данные, из которых frontend может отрисовать
пошаговое решение без самостоятельного пересчета:

- `input.employees[].months[]`: исходные строки РСВ `140` и `160`.
- `result.monthly_results[]`: месячные агрегаты: `labor_payment_sum = S(m)`, `headcount = K(m)`, `average = A(m)` и флаг участия месяца в квартальной средней.
- `result.quarter`: квартальные агрегаты: `months_with_payments = Mcnt`, `monthly_average_sum = Σ A(m)` и `average = A`.
- `result.threshold`: только выбранная планка `used = P` и ее источник; исходные значения планок уже есть в `input.threshold`.
- `result.comparison`: разница с выбранной планкой, процент разницы и вердикт.
- `result.recommendation`: готовые числа для рекомендации frontend.

Чтобы не дублировать данные:

- `total_140` и `gph_160` хранятся только в `input`.
- `L(i,m) = max(0, T(i,m) - G(i,m))` по каждому сотруднику не возвращается отдельным массивом; backend возвращает сразу `S(m) = Σ L(i,m)` в `result.monthly_results[].labor_payment_sum`.
- `period` хранится только в `input`; в `result` есть только `threshold_period`.
- исходные планки хранятся только в `input.threshold`; в `result.threshold` есть только примененная планка.
- итоговая средняя хранится в `result.quarter.average`; в `comparison` она не повторяется.
- примененная планка хранится в `result.threshold.used`; в `comparison` она не повторяется.

`recommendation.type` принимает значения:

- `CAN_DECREASE`: компания проходит аккредитацию, `delta > 0`; frontend может показать, на сколько теоретически можно снизить среднюю выплату без потери прохождения.
- `NEED_INCREASE`: компания не проходит аккредитацию, `delta < 0`; frontend может показать, на сколько нужно повысить среднюю выплату.
- `NO_THRESHOLD`: планка не задана, вердикт и рекомендация по прохождению не рассчитываются.

`comparison.verdict` является единственным полем для определения результата:

- `PASS`: компания проходит критерий аккредитации.
- `FAIL`: компания не проходит критерий аккредитации.
- `NO_THRESHOLD`: планка не задана, поэтому результат прохождения не определяется.

## Получить Список Расчетов

`GET /api/v1/calculations`

Требует авторизации через cookie `wagecalc_session`.

Возвращает только расчеты организаций, доступных текущему пользователю.
Ответ `200 OK`:

```json
{
  "items": [
    {
      "id": "calculation-id",
      "org_name": "ООО Ромашка",
      "title": "Аккредитация за III квартал 2025",
      "period": {
        "year": 2025,
        "quarter": 3
      },
      "checked_at": "2025-07-06T12:00:00Z",
      "quarter_average": "96666.67",
      "verdict": "PASS",
      "created_at": "2025-07-06T12:00:00Z",
    }
  ]
}
```

Поля списка:

- `id`: уникальный идентификатор расчета, сгенерированный backend.
- `org_name`: название организации для отображения и будущего поиска.
- `title`: название отчета для отображения и будущего поиска.
- `checked_at`: дата и время проверки, то есть момент расчета результата.
- `quarter_average`: итоговое среднее значение за квартал.
- `verdict`: строковый результат расчета: `PASS`, `FAIL` или `NO_THRESHOLD`.

## Получить Один Расчет

`GET /api/v1/calculations/{id}`

Требует авторизации через cookie `wagecalc_session`.

Возвращает расчет только если он доступен текущему пользователю. Если расчет не найден или принадлежит другому пользователю, backend возвращает `404 Not Found`.

Ответ `200 OK`: структура описана в разделе "Полный Ответ Расчета".

## Удалить Расчет

`DELETE /api/v1/calculations/{id}`

Требует авторизации через cookie `wagecalc_session`.

Удаляет расчет только если он доступен текущему пользователю. Если расчет не найден или принадлежит другому пользователю, backend возвращает `404 Not Found`.
Ответ `204 No Content`.
